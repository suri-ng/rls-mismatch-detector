# RLS Mismatch Detector

RLS Mismatch Detector compares what application code appears to allow with what PostgreSQL row-level security (RLS) policies enforce. It provides a web interface, an HTTP API, and a command-line interface for analyzing schema and source files together.

## Overview

An application may rely on a code-level filter that does not match its database policy, or assume that RLS protects a query that uses a privileged credential. This project analyzes the two sides independently and reconciles the resulting claims by table and operation.

The analysis is LLM-assisted. Treat findings as review guidance, not as a substitute for testing policies against the database or conducting a security review.

## Features

- Analyze one or more SQL schema files and application source files together.
- Inspect `SELECT`, `INSERT`, `UPDATE`, and `DELETE` access claims.
- Report a `MATCH`, `MISMATCH`, or `UNKNOWN` result with a severity and explanation.
- Run analysis through the Next.js UI, FastAPI endpoint, or Python CLI.

## How It Works

The pipeline has two independent analysis branches: the enforcement agent reads only the schema and RLS policies, while the access-model agent reads only application code. A reconciliation step pairs their claims by table and operation and produces the final results. The UI submits files to a Next.js API route, which forwards them to the FastAPI backend.

## Requirements

- Python 3.11 or newer for the backend
- Node.js 20 or newer for the frontend
- An OpenAI API key
- Docker Compose, if using the container setup

## Quick Start

### Run with Docker Compose

Create a `.env` file in the repository root with your API key:

```dotenv
OPENAI_API_KEY=your_openai_api_key
```

Build and start the services:

```bash
docker compose up --build
```

Open the UI at [http://localhost:3000](http://localhost:3000). The backend is available at `http://localhost:8001`. Stop the services with `Ctrl+C`; run `docker compose down` to remove the stopped containers.

### Run the UI Locally

In one terminal:

```bash
cd frontend
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). For scans, the UI also needs the backend running at `http://localhost:8000` (the default used by the frontend proxy).

### Run the Backend Locally

Set `OPENAI_API_KEY` in the repository-root `.env` file or export it in your shell. Then start the API in another terminal:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install fastapi uvicorn python-multipart
uvicorn api:app --reload --port 8000
```

The API accepts scans at `POST http://localhost:8000/api/scan`. It expects multipart form fields named `schema_files` and `app_code_files`, with at least one file in each field.

## Using the Application

In the UI, add one or more `.sql` files to **Schema** and one or more source files to **App code**, then start the scan. Results are shown by table and operation with a status, severity, and explanation. `UNKNOWN` means the available claims were insufficient to establish a match or mismatch.

## Example Output

For `case_01_missing_rls`, the app filters notes by the current user, but the database's `SELECT` policy allows all rows. A representative CLI result looks like this:

```text
notes.SELECT: MISMATCH / critical
	App code filters by user_id and assumes that is the only gate on who can read a note, but the RLS policy 'allow all reads' allows any authenticated (or anonymous) client to read every row directly via the auto-generated Supabase API, bypassing the app's filter entirely. Data exposure.
```

The table and operation identify the access being checked; `MISMATCH` is the comparison outcome, and `critical` is its severity. The explanation is generated by the LLM pipeline, so its exact wording may vary between runs.

## Command-Line Usage

Run CLI commands from the `backend/` directory so the package imports and bundled case paths resolve correctly.

Analyze a bundled case:

```bash
cd backend
python cli.py --case case_01_missing_rls
```

Analyze your own files (paths are relative to the current working directory):

```bash
python cli.py --schema ../path/to/schema.sql --app-code ../path/to/app.js
```

Both `--schema` and `--app-code` accept multiple paths. The CLI prints each result's table, operation, status, severity, and explanation. Set `OPENAI_API_KEY` before running either the API or CLI.

## Configuration

The backend loads environment variables from the environment or a `.env` file. Model defaults are currently `gpt-5.6-luna` for all three agents.

| Variable | Purpose | Default |
| --- | --- | --- |
| `OPENAI_API_KEY` | OpenAI API credential | Required |
| `ENFORCEMENT_AGENT_MODEL` | Enforcement agent model | `gpt-5.6-luna` |
| `ACCESS_MODEL_AGENT_MODEL` | Access-model agent model | `gpt-5.6-luna` |
| `RECONCILER_AGENT_MODEL` | Reconciler model | `gpt-5.6-luna` |
| `LLM_MAX_TOKENS` | Maximum completion tokens | `2000` |
| `LLM_TEMPERATURE` | Model temperature | `0` |
| `BACKEND_URL` | Backend URL used by the Next.js scan proxy | `http://localhost:8000` locally; `http://backend:8001` in Compose |

## Test Cases and Smoke Test

The `backend/test_cases/` directory contains paired schema and application-code examples with expected results in `expected.json`. Run the smoke test from `backend/` after setting `OPENAI_API_KEY`:

```bash
python smoke_test.py                  # all case folders
python smoke_test.py case_01_missing_rls
```

The smoke test calls the live LLM pipeline and prints comparisons against expected status and severity; results can vary with model behavior. `backend/eval/run_eval.py` is currently empty, so there is not yet a separate aggregate evaluation command.

## Troubleshooting

- **Missing API key:** set `OPENAI_API_KEY` in the root `.env` file or export it in the shell used to start the backend.
- **Scan returns an error:** confirm that at least one schema file and one app-code file were submitted, and inspect the backend terminal for the underlying error.

## Limitations and Security Notes

This is an LLM-assisted analysis tool; it does not execute SQL policies or prove that an application is secure. Review findings and validate important behavior against your database and application.

The scan API currently has no authentication and is intended for local or otherwise trusted use; do not expose it publicly as-is. Uploaded files are temporarily written by the API while a scan runs and are removed when the request completes. Their contents are sent to the configured OpenAI API as part of analysis, so do not upload secrets or data you are not permitted to share with that service.
